# Как внести изменение

Спасибо за вклад в API Writing Guide. Изменение должно решать конкретную проблему читателя и не противоречить действующим правилам.

## Предложить изменение

1. Проверьте поиск и открытые Issues: возможно, вопрос уже обсуждается.
2. Создайте Issue. Опишите проблему, аудиторию, ожидаемое правило и пример.
3. Для спорного или крупного изменения дождитесь согласования подхода.
4. Создайте ветку от актуальной `main`.

Назовите ветку по шаблону `тип/краткая-тема`, например:

- `docs/accessibility-rules`;
- `fix/broken-link`;
- `style/api-example`.

## Подготовить Pull Request

1. Внесите одно логически связанное изменение.
2. Для нового правила добавьте пару «неудачно / удачно» и критерий проверки.
3. Добавьте новую страницу в `nav` файла `mkdocs.yml`.
4. Выполните локальные проверки:

   ```bash
   python3 scripts/check_docs.py
   npx --yes markdownlint-cli2@0.23.3
   .venv/bin/mkdocs build --strict
   ```

5. Отправьте ветку и откройте Pull Request по шаблону.

## Оформить коммиты

Используйте [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```text
<тип>(<область>): <краткое действие>
```

Допустимые типы:

| Тип | Когда использовать | Пример |
| --- | --- | --- |
| `docs` | Добавление или изменение содержания | `docs(api): add pagination rules` |
| `fix` | Исправление ошибки | `fix(links): repair template link` |
| `style` | Правка оформления без изменения смысла | `style(home): align card spacing` |
| `chore` | Настройка инструментов и зависимостей | `chore(ci): enable strict build` |
| `refactor` | Перестройка структуры без нового правила | `refactor(nav): group templates` |

Пишите тему в повелительном наклонении, со строчной буквы, без точки в конце. Один коммит — одна законченная мысль.

## Пройти ревью

- Нужен минимум один одобривший рецензент.
- Автор отвечает на каждый содержательный комментарий.
- Исправления добавляются отдельными коммитами, чтобы их было удобно проверить.
- Обсуждение можно закрыть только после ответа или изменения.
- Перед слиянием все автоматические проверки должны завершиться успешно.
- После одобрения используйте **Squash and merge**.

Рецензент проверяет точность, однозначность правила, наличие примера, доступность текста, рабочие ссылки и место страницы в навигации.

## Добавить раздел

1. Создайте Markdown-файл в подходящей папке `docs/`.
2. Начните страницу с единственного заголовка H1.
3. Объясните цель правила до деталей его применения.
4. Добавьте минимум один проверяемый пример.
5. Включите страницу в `nav` файла `mkdocs.yml`.
6. При необходимости свяжите её с соседними разделами относительными ссылками.
7. Запустите проверки и откройте Pull Request.

Не добавляйте пустые разделы «на будущее»: сначала подготовьте полезное содержание.
