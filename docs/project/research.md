# Исследование стайл-гайдов

Перед проектированием изучены материалы из презентации к лабораторной и несколько зрелых руководств. Цель исследования — не собрать максимум правил, а выбрать решения, которые подходят русскоязычной документации REST API.

## Что такое стайл-гайд

Стайл-гайд — набор договорённостей о содержании, языке, структуре и оформлении документов. Для команды он выполняет три функции:

- превращает повторяющиеся редакторские решения в правила;
- снижает разнобой между авторами и версиями;
- задаёт критерии ревью и автоматической проверки.

Стайл-гайд не заменяет знание продукта, проверку фактов и редакторское мышление. Если правило ухудшает ясность конкретного документа, нужно зафиксировать обоснованное исключение и при необходимости уточнить само правило.

## Рассмотренные источники

### Материалы лабораторной

Презентация «Стайл-гайд1» задаёт базовую структуру: стиль изложения, орфография, оформление, Markdown, шаблоны, точечные рекомендации и глоссарий. Из неё также взят итеративный процесс: исследовать существующие документы, написать правила, протестировать, получить обратную связь и доработать.

### Google developer documentation style guide

[Руководство Google](https://developers.google.com/style) ориентировано на разработчиков и сочетает общие принципы с точечным справочником. Для проекта выбраны прямое обращение к читателю, действительный залог, содержательные ссылки, однозначные даты, семантическое оформление кода и alt-текст.

Полезное проектное решение: локальные правила имеют приоритет над общим внешним руководством. Это позволяет не копировать весь справочник, а фиксировать только решения, важные для конкретного продукта и русского языка.

### Ozon Tech

[Стайл-гайд Ozon](https://docs.ozon.ru/styleguide/) — пример русскоязычной продуктовой системы правил. Он показывает ценность словаря, конкретных формулировок и примеров «как писать / как не писать». Этот паттерн использован во всех ключевых разделах проекта.

### Diátaxis

[Diátaxis](https://diataxis.fr/) разделяет документацию по намерению читателя: обучение, решение задачи, справочник и объяснение. В проекте это отражено в выборе типа документа в быстром старте. Особенно важно не смешивать пошаговое руководство и полный справочник метода на одной странице.

### WCAG 2.2

[Web Content Accessibility Guidelines 2.2](https://www.w3.org/TR/WCAG22/) использованы как основа раздела доступности. Для редакционного процесса выбраны требования, которые автор может проверить: смысл не зависит только от цвета, ссылки описательны, заголовки последовательны, изображения имеют альтернативный текст, а управление доступно с клавиатуры.

## Выводы для проекта

1. Справочник должен быстро отвечать на точечный вопрос, поэтому правила сгруппированы по задаче, а не по лингвистической теории.
2. Каждое правило полезнее с причиной, примером и проверяемым критерием.
3. Для API недостаточно общих языковых рекомендаций: нужны поля, ошибки, идемпотентность, rate limit и безопасность примеров.
4. Шаблоны превращают правило в повторяемую практику.
5. Автоматизация проверяет форму, но точность и понятность требуют ревью человеком.
6. Стайл-гайд — живой продукт: изменения проходят тот же процесс веток, ревью и публикации, что и код.
