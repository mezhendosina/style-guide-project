# Отчёт по лабораторной работе № 3

**Тема:** разработка стайл-гайда на создание и оформление документации.  
**Цель:** освоить полный цикл Docs as Code на примере руководства по стилю.  
**Объект:** русскоязычная документация REST API для внешних разработчиков.

## 1. Изучение теории

Изучены презентация к лабораторной, Google developer documentation style guide, русскоязычный стайл-гайд Ozon, модель Diátaxis и рекомендации WCAG 2.2. Сравнение и выводы зафиксированы в разделе [«Исследование»](research.md).

Главный вывод: полезный стайл-гайд описывает не абстрактно «хороший текст», а повторяющиеся решения конкретной команды — аудиторию, виды документов, терминологию, структуру, оформление, инструменты и критерии качества.

## 2. Ответы на вопросы

### 2.1. Нужны ли стайл-гайды

Стайл-гайд нужен, когда документы создают или поддерживают несколько человек, продукт развивается длительно, а ошибка или неоднозначность создаёт заметные издержки. Он ускоряет работу: автор не принимает заново решения о терминах, структуре и формате, а рецензент обсуждает отклонение от известного критерия, а не личный вкус.

Не всегда нужен отдельный большой документ. Для одноразовой заметки одного автора стоимость создания полного руководства выше пользы. В небольшом проекте достаточно короткого чек-листа и словаря. Объём стайл-гайда должен расти вместе с повторяющимися вопросами и рисками. Даже зрелое руководство не заменяет проверку фактов и способность автора учитывать контекст.

### 2.2. Как использовать стайл-гайд

**До написания** автор выбирает тип документа и шаблон. Например, задача «создать заказ» получает структуру how-to, а точные свойства `POST /v1/orders` — структуру справочника метода.

**Во время написания** автор сверяется с правилами языка и словарём: обращается на «вы», использует один термин «метод API», оформляет `order_id` как код. API-раздел напоминает описать авторизацию, ограничения, ошибки и идемпотентность.

**На ревью** чек-лист превращает вкусовое обсуждение в проверку: назван ли результат, согласованы ли запрос и ответ, понятно ли действие при `429`, не передаётся ли смысл только цветом.

**В автоматизации** линтер проверяет Markdown, скрипт — локальные ссылки и навигацию, MkDocs — возможность строгой сборки. Например, забытая страница в `nav` останавливает CI до слияния.

### 2.3. Как использовать искусственный интеллект

ИИ полезен как ассистент, но не как источник истины. Его можно применять для:

- поиска повторяющихся формулировок и конфликтов в существующем корпусе;
- черновой кластеризации правил и терминов;
- генерации контрпримеров и граничных случаев;
- проверки текста по формализованному чек-листу;
- преобразования утверждённого правила в примеры и шаблоны;
- поиска потенциально недоступных, двусмысленных или обвиняющих формулировок.

Результат ИИ нужно проверять по реализации и источникам. Нельзя передавать модели секреты, персональные данные и закрытые документы без разрешения. ИИ не должен незаметно менять контракт API или придумывать ограничения. Ответственность за итоговое правило сохраняет автор и рецензент.

## 3. Выбор объекта

Выбран стайл-гайд для русскоязычной документации REST API, адресованной внешним разработчикам. В область входят справочники методов, практические руководства, примеры запросов, описание ошибок и короткие концептуальные статьи.

Выбор обоснован высоким риском неоднозначности. Неполное описание идемпотентности может создать дубликаты операций, ошибка в единице суммы — неверный платёж, а неясное описание `429` — лавину повторных запросов. Поэтому качество можно оценивать не только стилистически, но и по конкретным свойствам контракта.

## 4. Разработка стайл-гайда

### 4.1. Структура правил

Для каждого блока определены вопросы:

| Блок | На какие вопросы отвечает |
| --- | --- |
| Принципы | Для кого пишем? Как выбрать приоритет при конфликте правил? |
| Язык и тон | Как обращаться к читателю? Как строить действие и сообщение об ошибке? |
| Структура | Какой тип документа выбрать? В каком порядке дать сведения? |
| Оформление | Как обозначить код, UI, предупреждение, список и изображение? |
| Терминология | Как называть сущности единообразно? Какие варианты запрещены? |
| API | Какие части контракта обязательны? Как описать ошибки и повторы? |
| Шаблоны и проверка | Как быстро применить правила и проверить результат? |

### 4.2. Правила

Правила написаны в шести нормативных разделах. Основные требования: начинать с задачи читателя, использовать действительный залог и прямое обращение, давать одно действие на шаг, сохранять один термин для понятия, описывать полный API-контракт и проверять рабочий путь.

Каждое ключевое правило содержит объяснение, пример или критерий. Полный текст доступен в разделах [«Принципы»](../rules/principles.md), [«Язык и тон»](../rules/language.md), [«Структура»](../rules/structure.md), [«Оформление»](../rules/formatting.md), [«Терминология»](../rules/terminology.md) и [«Документация API»](../rules/api.md).

### 4.3. Структура стайл-гайда

Руководство организовано от общего к прикладному:

1. главная и быстрый старт;
2. нормативные правила;
3. шаблоны и чек-лист;
4. готовые примеры;
5. исследование и отчёт.

Такая структура поддерживает два сценария: новый автор проходит быстрый старт последовательно, опытный открывает точечное правило через навигацию или поиск.

### 4.4. Фиксация правил

Правила зафиксированы в Markdown и включены в `nav` файла `mkdocs.yml`. Сайт использует MkDocs Material, поиск на русском и английском, светлую и тёмную темы, адаптивную вёрстку и отдельные стили проекта. Каноническим источником является репозиторий, а не собранный HTML.

## 5. Тестирование

По стайл-гайду подготовлены два документа: [создание заказа](../examples/create-order.md) и [обработка ошибок](../examples/error-handling.md). При тестировании обнаружены неоднозначная денежная единица, риск дубликата запроса, неопределённая задержка повтора и отсутствие опорного `request_id`. После применения правил дефекты исправлены.

Подробная методика, матрица результатов и ограничения эксперимента приведены на странице [«Результаты тестирования»](../examples/evaluation.md). Вывод: руководство пригодно для пилота; следующая итерация должна включать двух независимых авторов и проверку запросов против sandbox API.

## 6–10. Репозиторий, MkDocs, линтинг и CI/CD

Подготовлен проект `style-guide-project` со следующими средствами:

- `mkdocs.yml` — структура, тема, поиск, расширения и строгий режим;
- `requirements.txt` — зафиксированная версия MkDocs Material;
- `.markdownlint-cli2.yaml` — правила линтинга Markdown;
- `scripts/check_docs.py` — проверка H1, локальных ссылок и полноты навигации;
- `.github/workflows/ci.yml` — проверки Pull Request и публикация `main` в `gh-pages`;
- `README.md` — локальный запуск и структура проекта.

CI выполняет проверку структуры, Markdown-линтинг и `mkdocs build --strict`. Деплой начинается только после успешного quality job.

## 11. Ветки и Pull Request

Для учебного изменения подготовлены отдельная ветка, шаблон Pull Request и процесс ревью. Точные команды и порядок публикации приведены в корневом файле `SUBMISSION.md`.

Создание репозитория, обмен с одногруппником, три комментария, повторный коммит, одобрение и merge требуют личных GitHub-аккаунтов. После выполнения нужно приложить ссылки и скриншоты в поля ниже.

## 12. Документирование процесса

Файл `CONTRIBUTING.md` описывает предложение изменения, ветки, Conventional Commits, локальную сборку, добавление раздела, обязательные проверки и процесс ревью. Шаблон `.github/PULL_REQUEST_TEMPLATE.md` превращает требования в чек-лист автора.

## Итог

Создано применимое руководство по стилю с правилами, шаблонами, апробацией и автоматическим контролем качества. Docs as Code делает изменение прослеживаемым: оно проходит ветку, Pull Request, ревью, сборку и автоматическую публикацию.
