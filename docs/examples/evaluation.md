# Результаты тестирования стайл-гайда

Стайл-гайд протестирован на двух типах практической документации: пошаговом сценарии [«Создание заказа»](create-order.md) и инструкции [«Обработка ошибок API»](error-handling.md). Цель теста — проверить не красоту формулировок, а достаточность и применимость правил.

## Методика

Для каждого документа выполнены четыре прохода:

1. **Проектирование:** определены читатель, задача и критерий успеха.
2. **Написание:** применены правила языка, структуры, API и оформления.
3. **Редакторская проверка:** заполнен [чек-лист](../patterns/checklist.md).
4. **Техническая проверка:** проверены ссылки, навигация, Markdown и строгая сборка MkDocs.

Так как API учебный, сетевые запросы не отправлялись. Оценивались внутренняя согласованность, полнота контракта и возможность перенести пример на реальный API.

## Какие дефекты нашли правила

Во время первого прохода были обнаружены и исправлены четыре проблемы:

1. Сумма была указана как `1299` без единицы. Добавлено объяснение минимальных денежных единиц.
2. Повтор запроса после сетевой ошибки мог создать дубликат. Добавлен `Idempotency-Key` и срок хранения результата.
3. Рекомендация «повторить позже» была неизмеримой. Добавлены предел попыток, интервалы и правило `Retry-After`.
4. Сообщение об ошибке не давало опорного идентификатора. Добавлено поле `request_id` и правило журналирования.

## Оценка качества

Стайл-гайд признан пригодным для пилотного использования. Он помогает создать короткий рабочий сценарий, не пропустить параметры безопасности и согласовать язык. Сильные стороны — проверяемые формулировки, шаблоны и связь правил с автоматическими проверками.

Ограничения пилота:

- использован учебный, а не работающий API;
- тестировал один автор, поэтому не измерена согласованность между авторами;
- не проверены release notes, концептуальные статьи и интерфейсные инструкции;
- ручная проверка экранным диктором не проводилась.

## Следующая итерация

Для повышения надёжности нужно дать одинаковое задание двум авторам, сравнить структуру результата и зафиксировать неоднозначные решения. Затем протестировать примеры против sandbox API и добавить автоматическую проверку OpenAPI-схемы.

Критерий следующей версии: два автора независимо получают одинаковый порядок разделов, используют одинаковые термины и не пропускают обязательные свойства метода API.
