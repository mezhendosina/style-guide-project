# Документация API

Справочник API описывает проверяемый контракт. Практические руководства показывают, как использовать этот контракт для задачи.

## Описывайте метод в фиксированном порядке

Для каждого метода укажите:

1. HTTP-метод и путь;
2. назначение и права доступа;
3. требования к авторизации;
4. параметры пути и строки запроса;
5. заголовки;
6. схему тела запроса;
7. полный рабочий пример;
8. успешный ответ;
9. ошибки;
10. ограничения, идемпотентность и лимиты.

Используйте [шаблон метода API](../patterns/api-method.md), чтобы не пропустить раздел.

## Формулируйте описание параметра

Описание отвечает на вопросы «что это», «зачем нужно» и «какие ограничения действуют». Не повторяйте имя и тип.

=== "Неудачно"

    `customer_id` — ID клиента. Строка. Обязательно.

=== "Удачно"

    `customer_id` — идентификатор клиента, от имени которого создаётся заказ. Получите его методом `GET /v1/customers`. От 1 до 64 символов.

Для каждого поля фиксируйте обязательность, тип, формат, допустимые значения, значение по умолчанию и возможность передать `null`.

## Синхронизируйте запрос и ответ

Значения в примерах должны согласовываться. Если запрос содержит `customer_id: "cus_123"`, ответ не должен без объяснения возвращать `cus_999`. Даты, суммы и статусы должны формировать правдоподобный сценарий.

## Разделяйте HTTP-статус и код ошибки

Укажите оба уровня:

| HTTP | Код | Когда возникает | Действие клиента |
| --- | --- | --- | --- |
| `400` | `invalid_request` | Запрос нарушает схему | Исправить указанные поля |
| `401` | `unauthorized` | Токен отсутствует или недействителен | Передать действующий токен |
| `404` | `order_not_found` | Заказ не найден или недоступен | Проверить ID и проект |
| `409` | `idempotency_conflict` | Ключ повторён с другим телом | Использовать новый ключ |
| `429` | `rate_limit_exceeded` | Превышен лимит запросов | Повторить после `Retry-After` |

Не описывайте `400` как универсальный ответ на все ошибки: читателю нужен способ различить причины.

## Объясняйте повторные запросы

Для изменяющих состояние методов укажите:

- является ли операция идемпотентной;
- какой заголовок или ключ предотвращает дублирование;
- сколько хранится результат;
- какие ошибки можно повторять;
- какую задержку использовать.

Рекомендуйте exponential backoff с jitter для временных ошибок, но приводите конкретные пределы, если API их устанавливает.

## Защищайте данные в примерах

Используйте вымышленные домены `example.com`, тестовые идентификаторы и заполнители. Не публикуйте реальные токены, номера телефонов, адреса, ФИО и платёжные данные — даже если они уже недействительны.

## Отмечайте версии и изменения

Указывайте дату удаления устаревшего поведения и путь миграции. Не используйте «скоро» без даты. Для несовместимого изменения опишите:

- кого оно затрагивает;
- старое и новое поведение;
- необходимые действия;
- крайний срок;
- способ проверить миграцию.
